Section 01

Architecture & Module Structure

How the app is organized, why it's vanilla JS, and how modules communicate.

Why did you use vanilla JavaScript instead of React or Vue?

The scope is small — seven tables, ten pages, no complex component trees. A framework would have added a build step, npm tooling, and bundle size without solving any problem I actually had.

The trade-off: no component reuse, manual DOM updates, and no reactivity. Fine for this size, painful for anything larger.

How do the modules communicate with each other?

Three mechanisms, each used where it fits:

  • Shared namespace — each IIFE attaches its public API to window.AsniApp. So App.Render, App.State, App.Auth are all siblings on the same object.
  • Custom DOM events — asni:theme-changed and asni:role-changed. Charts and the dashboard listen for these and re-render themselves.
  • Direct calls — when there's a strict dependency, like router.js calling into App.Modals.
Why does the order of <script> tags matter?

Because modules read from each other at load time. render.js does const db = App.State.db at the top — if state.js hasn't run yet, that line throws a TypeError and the entire module fails to register. Same for api.js reading App.Keys and App.Tables from keys.js.

There's no bundler and no module resolver — the order in index.html is the dependency graph.

Why wrap each module in an IIFE?

Encapsulation. Variables inside (function(App){ … })(window.AsniApp) don't leak to global scope. Only what's explicitly assigned — App.Render = {…} — becomes public.

Section 02

Theming & CSS

CSS custom properties, role accents, and the theme toggle.

How does the dark/light toggle work?

theme.js sets document.documentElement.setAttribute('data-theme', 'dark'|'light'). Every color in style.css is a CSS custom property defined on :root and overridden on [data-theme="light"].

Flipping one attribute changes every color in the app. No class shuffling, no inline styles, no re-render.

Why CSS custom properties instead of Sass variables?

Custom properties can change at runtime on any element; Sass variables are compile-time constants. Since the theme flips live, custom properties are the correct tool.

You load Tailwind but barely use it. Why?

It was a starting scaffold that never got removed. The final CSS is 95% custom. The Tailwind CDN adds ~70 KB gzipped for two utility classes (h-full and hidden) that are both already in style.css.

Honest answer: it should have been removed. It's the biggest single performance win available.

How does the role-based accent color work?

body.role-admin, body.role-receptionist, body.role-guest each define --role-accent, --role-accent-soft, --role-accent-text. Every component that wants a role-tinted border or background reads the token.

One class swap on <body> re-themes the shell, the sidebar active state, the top accent bar, and the login button.

How did you handle responsive design?

Mobile-first media queries at 480, 640, 768, and 1024 px. The sidebar becomes an overlay under 768px. Table columns hide via .hide-sm, .hide-md, .hide-lg. The KPI grid goes 4 → 2 → 1 columns.

Section 03

Rendering & DOM

XSS escaping, innerHTML trade-offs, and the state reference gotcha.

How do you prevent XSS?

Every string that comes from the database is passed through App.Utils.esc() before being concatenated into innerHTML. esc() replaces & < > " ' with their HTML entities.

The limits: this handles the common cases but isn't a full sanitizer. A stricter approach would use textContent everywhere — but that costs readability.

Why innerHTML instead of createElement?

Readability and speed of writing. A template literal is much shorter than a series of createElement + appendChild calls, especially for tables with 8+ columns.

Trade-off: parse cost on every render, plus the XSS risk above.

Why does render.js capture db at module load?

render.js does const db = App.State.db at the top — it captures a reference to the object, not a copy.

When app.js loads data, it must call Object.assign(App.State.db, freshData), not App.State.db = freshData. If it reassigns, the render module still points at the old empty object and every table renders empty.

I hit this bug during development — all tables were empty after a successful fetch. Root cause was reassigning instead of mutating.

How do you handle chart re-renders?

charts.js keeps instance references — revenueChartInst and categoryChartInst. Before creating a new chart on the same canvas, it calls .destroy() on the previous instance.

Skipping the destroy is a classic Chart.js bug: stale canvas state, duplicated listeners, and eventually a memory leak.

Section 04

State & Data Flow

Single shared object, imperative re-render, and offline fallback.

Where does application state live?

One object: App.State.db, initialized in state.js with empty arrays for every table. It's loaded from the D1 API in app.js via App.Api.loadAllFromD1(). Every module reads from this single object and re-renders from it.

How does the UI stay in sync with the data?

Imperatively. Every write operation — dbInsert, dbUpdate, dbDelete — calls App.State.reload(), which re-fetches everything and calls App.Render.renderAll().

It's not reactive — it's a full re-render on every mutation. Fine for this scale, painful for larger datasets.

Why not Redux, Zustand, or signals?

Same reason as no framework — no build step, no dependencies, small scope. renderAll() after every mutation is simpler to reason about than wiring up an observer system.

What happens if the API is offline?

App.Api.online flips to false. state.js falls back to localStorage via loadLocalCache(). Writes go to memory and persist to localStorage instead of D1. When the API returns, the next reload() overwrites local changes — a known limitation.

Section 05

Auth & Roles

Client-side auth, role gating, and the honest security answer.

How does authentication work?

Users pick a role (Admin, Receptionist, or Guest). Staff roles require a password; the password is compared against the password column in the users table.

On success, a session object is stored in localStorage (if "Remember me" is checked) or sessionStorage (if not).

Is this secure?

No, and I want to be direct about that. It's client-side authentication. Anyone with DevTools can edit localStorage.asni.session and set role: 'admin', or call /api/query directly.

Real auth needs a /api/login endpoint on the Worker, server-side password hashing, and a signed session token required on every query.

How does role gating work?

Two mechanisms:

  • data-roles attributes on nav buttons and dashboard elements — setRole() toggles is-hidden on anything whose role list doesn't include the current role.
  • .can-edit class on buttons — hidden for guests.

Both are cosmetic. Removing display: none in DevTools reveals the buttons.

Why is Guest the default?

Because most visitors aren't staff — they just want to see rooms and the menu. Forcing a login for public content is bad UX. Staff opt in to elevation via the toolbar door icon.

Section 06

Performance

What's slow, what's fast, and what would be fixed first.

What's the biggest performance issue?

Blocking CDN requests in <head> — Tailwind, Chart.js, Font Awesome, and Google Fonts. None are async or deferred. On a slow connection the page is blank until all four finish.

Biggest win: removing Tailwind (~70 KB gzipped for two utility classes).

How many network round-trips on load?

One health check, then seven parallel table queries. Promise.all fires them together, so it's effectively one round-trip of latency, not seven.

Does the app work offline?

Partially. Last loaded state is cached in localStorage and rendered on next load if the API fails. Reads work; writes go to memory + cache and are lost on the next successful reload().

Section 07

Accessibility & UX

Keyboard, screen readers, and the improvements that mattered.

Does keyboard navigation work?

Partially. Tab order is natural. Modals don't trap focus — you can Tab out of a modal into the page behind it. Escape closes most modals. Not audited for full WCAG compliance.

What about screen readers?

Icon-only buttons have title attributes but not always aria-label. Form labels aren't associated with inputs via for/id. A real gap I should have done better on.

Any UX improvements you're proud of?

The boot-gate fix: adding body.is-booting with .app-body { visibility: hidden } until App.boot() completes. Before that, the dashboard flashed briefly before the login modal appeared — that's now gone.

Section 08

Honest Weaknesses

Traps teachers set. Have real answers — don't get defensive.

These are probes, not attacks. They're testing whether you understand your own trade-offs. Answer honestly, name the limitation, and propose a fix.
If you started again, what would you do differently?
  • Use real ES modules with import/export instead of window.AsniApp
  • Remove Tailwind, keep pure custom CSS
  • Add a small build step (Vite) — not a framework, just bundling
  • Real server-side auth from day one
What's the worst part of this codebase?

Two honest answers: (1) the render.js reference capture of App.State.db is fragile — it works only because every writer mutates instead of reassigning. (2) innerHTML + manual escaping is one bug in esc() away from an XSS hole.

How would you scale this to fifty guest houses?

Multi-tenant DB with a tenant_id column on every table. Real auth with real sessions and permissions. Probably a framework at that point — the manual re-render model gets unwieldy fast.

Show me a bug you fixed.

Pick one and tell the story:

  • State reference bug — reassigning App.State.db broke render's captured reference
  • Chart instance leak — recreating without destroy caused memory growth
  • Boot-order flash — dashboard visible before login modal
  • Role-gating regression — is-hidden class was applied but no generic CSS rule existed to honor it outside nav buttons

Task 7 — Find a planted bug

Prompt: "Something is broken. Find and fix it."

Common plants and how to spot each:

  • Missing data-roles — an admin-only button appears for guests. Search the HTML for the button.
  • Renamed state property — swap App.State.db for App.State.data in one file. Console shows a TypeError on the first access.
  • Swapped script order in index.html — load-order crash. Console shows Cannot read properties of undefined.
  • Removed is-hidden CSS rule — role gating silently stops working; the class is added but has no effect.

Strategy: open DevTools console first. Look for the error. Trace it to the file and line. Fix the smallest thing that matches.

What they're testing: can you debug with tools rather than guessing.

Section 10

Live Demo Walkthroughs

The questions where they want you to trace an interaction end-to-end.

Most likely single question: "Walk me through what happens when I click the door icon in the footer." Have this down cold. Being able to trace one interaction through every module proves you built it rather than assembled it.
Walk me through what happens when I click the door icon.

When a guest clicks it:

  1. updateLoginButton() wired an onclick when the app booted — it captured the current isGuest() state at that moment
  2. Since the user is a guest, it calls openLoginModal()
  3. openLoginModal() fetches users if not already loaded, then shows the modal, binds the form's submit handler, and populates the role dropdown
  4. syncLoginForm() hides the password field when Guest is selected (guest has no password)

When a signed-in staff member clicks it:

  1. onclick sees isGuest() is false
  2. Calls logout() — removes asni.session from both storage locations
  3. Calls applyRoleToShell('guest') — drops the UI to guest role via Router.setRole
  4. Calls updateLoginButton() — swaps the icon back to fa-right-to-bracket
  5. Shows a toast confirming the sign-out

No page reload. The button flips role in place.

Show me a role switch in action.

Click into the sidebar's role dropdown (visible only when signed in as admin). Pick a different role. Watch:

  • Sidebar nav buttons hide/show based on their data-roles
  • Dashboard KPIs and the revenue chart disappear for guest
  • Edit buttons (.can-edit) vanish for guest
  • The top accent bar changes color
  • An asni:role-changed event fires and charts redraw
And when I refresh the page — what order do things happen in?
  1. keys.js runs first — defines App.Keys and App.Tables
  2. theme.js — reads saved theme preference from localStorage
  3. api.js — sets base URL from localStorage
  4. state.js — initializes empty App.State.db
  5. auth.js, charts.js, render.js, modals.js, router.js — register their public APIs on window.AsniApp
  6. app.js — the last file, wires everything and calls App.init()
  7. App.init() → theme applied → auth bootstrap (guest or existing session) → App.boot() → health check → 7 parallel table queries → renderAll() → is-booting removed
What does the boot gate do?

body.is-booting sets .app-body { visibility: hidden }. The main content area is invisible until App.boot() finishes, so users never see the flash of a half-rendered dashboard behind the login modal.

Once boot completes, document.body.classList.remove('is-booting') reveals the shell.

Preparation Checklist
What should you do the night before?
  • Dry-run Tasks 1, 2, and 3 on a copy of the project. Undo them. Do them again. Muscle memory matters more than reading.
  • Keep modals.js, render.js, and router.js open in editor tabs. When they ask "where would you add X?", point and show instead of scrolling.
  • Have DevTools open on the console. Half the time the fastest answer is "let me look at the console."
  • Practice the door-icon walkthrough out loud. Three times. No notes on the last pass.
What NOT to do. Don't say "I'll just look it up" if you blank. Instead: "I'd check whether the data is reaching the render function — I'd log it in the console." Shows process, buys time. Teachers respect that over freezing.
